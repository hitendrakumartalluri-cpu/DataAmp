# AMP 0.11.0-beta.1 — Archive, index and search

This beta implements a usable local archive workflow and issue-driven workbench on top of the connector baseline. It is a development beta, not production certification. The gateway remains retired. The scope is all 27 existing GitHub issues, with working slices and explicit deferred deliverables; no issue is automatically closed by this release.

## Start and exercise

```bash
git checkout beta/0.11-archive-platform
./scripts/run-beta.sh
```

Open http://localhost:8080. Python 3.12+ is recommended. The script creates a virtual environment, installs runtime dependencies, uses SQLite and persists data under `data/`. It binds to localhost. Alternatively, `docker compose up --build` starts AMP and PostgreSQL. Docker and live PostgreSQL have not been exercised in the local build environment; the PostgreSQL contract runs in CI. Demo mode is enabled for these local examples.

1. Open **Archiving**. The seeded profile and invoice demonstrate accepted, archived and search-visible states. The worker runs every two seconds.
2. Choose a profile, upload a document with business ID, revision, idempotency key and JSON metadata. An accepted response indicates durable staging; inspect the receipt to confirm ARCHIVED.
3. Search by text and metadata filters, inspect reconciliation, and download the verified archived payload.
4. Use **Exports & evidence** to queue an export or evidence pack. Download through an owner-bound token after completion.
5. Use **Design tools** for schema, query, capacity, cost, governance and optimization plans. **Access & audit** configures grants and denies. **Beta coverage** exposes runtime qualification labels.

The seeded invoice is a plain text example. Optional Tika extraction and encrypted-PDF detection are supported; password recovery is outside scope. Documents with no extractable text remain metadata/name searchable.

## Supported source and mechanism boundaries

| Source/mechanism | Current beta behavior | Qualification |
|---|---|---|
| AMP multipart API | Durable single-document acceptance with metadata | HTTP regression tested; default upload limit 1 GiB |
| ZIP/TAR packages | JSON/CSV/XML manifests, traversal/link guards and per-item partial results | Local package and API contracts tested; max 10,000 items, 1 GiB expanded bytes |
| Mounted SMB/NFS/local share | Ready-marker manifest collection through a locally mounted path | Filesystem contract tested; AMP does not mount or manage SMB credentials |
| MFT landing zones | An external MFT product deposits ready manifests/packages or calls AMP API | Transport agnostic; no AMP AS2/EDI/partner-management server |
| SFTP | Strict known-host verification, ready marker, bounded download and checksum | Adapter present; real server required |
| S3-compatible/Azure object source | Explicit key-list collector, source version pinning and recursion exclusion | Adapter present; real provider required; max 1,000 keys per call |
| Hop | Approved read-only pipelines receive a search manifest through a shared mount | External adapter requires Hop Server route/auth/runtime qualification |
| SaaS/application sources | Can submit documents and mapped metadata through API/packages today | Native SharePoint, M365/email, Box, databases/CDC, ERP/SAP and other specialist adapters deferred |
| Continuous capture/scheduling | Existing connector change-adapter scaffolding; archive worker drains accepted items/jobs | Archive collectors are manually/API invoked; distributed scheduling, transfer continuation and CDC-to-archive are deferred |

Destinations are LOCAL (tested integrity), AWS/S3-compatible (SDK mock contract), and Azure Blob (adapter). HCP S3/VSP use an explicitly configured compatible adapter; native HCP REST writes and GCS writes are absent. Generic “output of choice” uses a future destination plugin contract, not arbitrary unvalidated output execution.

S3 native retention/hold requires `options.archive_object_lock_verified=true` only after independently qualifying the destination bucket, versioning, Object Lock and permissions. The receipt verifies payload AND metadata protection. A flag alone is not certification. Azure immutable-storage protection has no verified beta implementation. Required unsupported protection quarantines the record rather than reporting success. Local files and local audit tables are editable by administrators and are not compliance-grade WORM.

## Configuration and operational limits

Profiles require `destination_group_id`, source kind API/MOUNT/SFTP/OBJECT, and optional typed `mapping` and `protection`. Configure source/destination storage and catalogue groups under Connections. Mount manifests require `<manifest>.ready`; use the sample in `examples/archive/`. Source objects are never deleted. Destination configuration is pinned when the profile is created; create a new profile for changes.

For real identities set `AMP_DEMO_MODE=false`, and configure `AMP_IDENTITIES_JSON` as a JSON object keyed by SHA-256 of bearer tokens. Each entry contains `tenant`, `actor`, `roles` and `groups`. Only a server-configured admin role bypasses access maps. A configured `AMP_API_KEY` is an operator credential restricted to the default tenant. With neither configured, non-demo API access is rejected. The console Access button stores supplied credentials in this browser's local storage; use a trusted local testing environment. SSO, credential vaults, production TLS and CORS policy need their deployment integration.

Non-admin identities default deny. Add matching grants with `/api/v1/beta/access-maps`; denies take precedence. Legacy operator endpoints require explicit `tenant_id` for non-default tenants and reject cross-tenant resource IDs. Download authorization is checked again against the current projection.

Use one API process/worker in this beta. Archive processing has a one-hour lease and up to five automatic attempts, without backoff; inspection and manual retry are available. A crashed process restarts transfers from durable staging; this is not cross-process multipart continuation. Archive payloads already completed are read/verified before retry. A search failure cannot roll back an archive receipt. Export jobs left RUNNING after process loss require operator recovery; external Hop acknowledgment is not pipeline completion proof. Do not blindly replay a Hop run. Staging is retained for recovery; disk-capacity policies and lifecycle cleanup are follow-on work.

The beta search engine is a bounded local reference implementation, not a live federated Solr deployment. Export, facet and scan snapshots are capped at 10,000 records; this does not prove enterprise scalability. SQL metadata scans are unbounded before this cap and need scale work. PII text scans are capped at 1 MiB/document. AI-labelled tools are deterministic helpers, not deployed LLM features. Governance, optimizer and bulk mutation plans do not modify source objects.

## Verification

```bash
python -m pip install -r services/control-plane/requirements-test.txt
./scripts/beta-regression.sh
```

Local build evidence: **28 tests passed**, Python compilation, both JavaScript syntax checks and shell syntax checks passed. Nine console views loaded under jsdom with live local API calls; this is DOM/API verification, not visual browser review. S3 multipart/version retrieval was tested with Moto; protection request/readback contracts use captured SDK requests and explicit Stubber responses because Moto's retention route is incompatible with the installed SDK. No real S3/Azure/HCP/SFTP/Hop endpoint, browser-rendered visual QA, Docker deployment or PostgreSQL execution is claimed by that local evidence. CI includes a dedicated PostgreSQL contract job; consult its result on the pull request.

Release gate for customer pilots: pass PostgreSQL CI, perform rendered browser review, qualify at least one real destination and source, validate native protection and backend-authoritative evidence where required, exercise restart/disk-capacity cases and measure a representative workload. Keep unresolved issue acceptance criteria open.
